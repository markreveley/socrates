# Review — the 0001 build, the docs, and the tutorial

## Verdict

**The build is faithful.** Spec, tests, tutorial, and binary agree with each
other to a degree that is rare: the 98-test suite passes on the pinned
toolchain; scenarios 1–7 reproduce byte-for-byte from the built escript
(modulo declared nondeterministic values); every audit amendment (A2–A4,
B1–B5, C1–C3) is visible in the shipped behavior; and the tutorial's line
references are currently *exact*, not approximate. The findings below
(R1–R8) are minor — two small behavioral inconsistencies, one unratified
asymmetry worth a decision, and a handful of nits. Nothing blocks use;
nothing contradicts a ratified decision.

**The docs are unusually coherent.** The normativity layering (canon
verbatim → plans/specs decide → docs explain) is declared in every front
matter and honored in the text. The research spike argues against its own
repo where the evidence demands it, which is the strongest credential
explanatory docs can carry.

**The gap is not in the artifacts — it is that the store does not exist.**
Plan 0001's store section says the dogfood store is "this repo, committed";
M1's promise is "the operator can begin authoring socrates-in-socrates."
There is no `.socrates/` in the repo. The system is built, documented,
researched, and unused on itself. That gap is the subject of the companion
study filed with this review ([docs/04-transfer-study.md](../docs/04-transfer-study.md)).

## B. Findings — build

Ordered by substance; none blocking. Line references are to the tip this
review was run against (15b082a).

- **R1. `show` counts dead dependents; `rdeps` lists live ones.**
  `cmd_show`'s rdeps count (`lib/socrates/cli.ex:372-377`) counts every
  journaled dependent regardless of state; `rdeps_map`
  (`lib/socrates/cli.ex:473-483`) filters to `proposed | ratified`.
  Reproduced: a def whose only dependent was rejected shows `rdeps: 1`
  while `rdeps` prints nothing. Neither surface is spec-pinned (cli-v0
  pins `show`'s field list, not the count's semantics), so this is an
  inconsistency, not a violation. Propose: count live dependents, matching
  the query surface the operator will actually follow the number into.
- **R2. `show` renders a nil request id as an empty slot.** The footer
  prints `-` for a nil request id (`lib/socrates/cli.ex:1058`); `cmd_show`
  interpolates it raw (`lib/socrates/cli.ex:386`), producing
  `provenance: fixture ·  · 0 in / 0 out`. One character of missing
  parity between the two provenance surfaces.
- **R3. Self-referential defs: the two doors disagree, and neither was
  asked.** An operator `add` of a def whose body uses its own term is
  refused — `E_TERM_UNDEF`, because `check_operator` resolves terms
  against the store fold, which cannot yet contain the candidate
  (`lib/socrates/gate.ex:81-96`). A model artifact def doing the same
  passes — `check_artifact`'s term scope includes the artifact's own defs,
  the def under check among them (`lib/socrates/gate.ex:59-64`). Both
  behaviors are defensible (a circular definition arguably deserves
  refusal; a def elaborating on its own term arguably doesn't), but they
  are different, undocumented, and unratified. Consequence for operators:
  mutually-referring defs require add-then-amend ordering. Propose:
  decide the rule once — either exclude a def's own term from its body's
  scope at both doors, or admit the candidate's term at both — and note it
  in loadout-v0 § the term rule.
- **R4. `verify`'s foreign-object sweep skips dotfiles.**
  `Path.wildcard("sources/**")` defaults to `match_dot: false`
  (`lib/socrates/cli.ex:609-616`), so a planted `.hidden` file under the
  verbatim area escapes `UNRECORDED`. One-line fix (`match_dot: true`).
  Pedantic, but this is a tamper-evidence surface; N14 calls a foreign
  object in the verbatim area a tamper signal.
- **R5. README's status line outruns the acceptance record.** The README
  front matter says "acceptance walked"; build notes § Acceptance says
  steps 1–5 walked, **step 6 pending the operator's run** (live intake
  from the escript — the TLS path that B1 exists for). One clause would
  restore parity: "acceptance walked under the fixture; live-escript
  intake pending."
- **R6. Tutorial arithmetic nit.** "Nine modules plus the CLI" — the
  module map below it lists ten non-CLI modules (the Client behaviour and
  its two implementations are three files). Counts as written: 10 + CLI,
  2,491 lines (the "~2,500" is right).
- **R7. A malformed `fixture:<path>` file crashes rather than exiting 2.**
  `from_path/2` calls `File.read!`/`JSON.decode!`
  (`lib/socrates/client/fixture.ex:40-44`); an unreadable or non-JSON path
  surfaces as a raised exception with a stack trace, not the orderly
  `exit 2` a usage error gets. Test-surface only; still the one door where
  the CLI's error posture leaks.
- **R8. Two provenance surfaces, two totals.** For a multi-call intake the
  footer sums usage across calls (N24); `show`'s provenance line prints
  the last call's usage alone (`lib/socrates/cli.ex:379-387`). Both are
  true statements about different things; nothing labels which. Propose:
  sum in `show` too, or label the line `last call:`.

Also noted, no action: tutorial §6 says the sort is "not a queue-based
Kahn" while `graph.ex`'s moduledoc says "(Kahn)" — N11 already reconciles
these (depth-layering *is* Kahn taken a ready-set at a time), so the only
cost is a reader reconciling them via N11.

## C. The docs, reviewed

**docs/01-purpose.md — right register throughout.** The three-observation
diagnosis is a faithful unpacking of canon §3 with the quotes verbatim; the
"what socrates is not" section does real boundary work (the proof-assistant
and guardrails distinctions matter and are drawn accurately); and the
closing section keeps the purpose claims in hypothesis register ("the
load-bearing untested assumption is adoption"), which matches both canon's
own "that's the dream anyway" and the research spike's verdicts. No drift
found against canon, plan, or code.

**docs/02-architecture.md — matches the build as verified.** Every
mechanism described was exercised by this review and behaved as written:
the six types and the two language rules, sid-vs-display identity, the
derived and never-read `definitions.json`, the gate table, the two-door
asymmetry, the life-of-a-statement walk (which is scenarios 4–7
compressed, accurately). The one soft spot is shared with the README (R5):
"Acceptance for the whole build is exactly this walk" is true of the
fixture-canonical path and silent about the pending live step.

**docs/03-research-spike.md — the standout document.** Its verdicts run
against interest where the evidence demands (adoption risk named the
weakest link; the canary's own alert diagnosed as warning-fatigue-prone;
two canon phrasings flagged as outrunning their evidence, with the
annotations filed here precisely because canon is verbatim-frozen). The
inward-facing characterizations were spot-checked against the repo and
hold: the gate limit (T9) is stated in plan 0006 in nearly the quoted
words; the lineage table's "accurate-with-nuance" entries match what
README actually claims. External citations were not re-verified by this
review (out of scope; the spike's method section says a per-cluster agent
verified them against publishers on 2026-08-05).

**docs/README.md** — the reading order and the non-normativity banner do
their job. The transfer study filed alongside this review is added there
as item 4.

## D. The tutorial, reviewed

**docs/code-walkthrough.md is accurate to the letter at tip.** Checked:
the module map (files, one-liners), the journal example's field order
against `Statement.to_pairs/1`, §3's `emit/1` "line ~116" (exact), §3c's
"fold/1 (line ~231)" (exact), §10's `cmd_intake ~713` / `intake_loop ~772`
/ `accept_artifact ~924` (all exact), the ULID arithmetic (2+48+80 = 130 =
26×5), the fixture's round derivation, the 98-test count, and both
end-to-end traces against the code paths they narrate. The hedge in its
header ("line references are approximate beyond that commit") is currently
unneeded and will become load-bearing with the first edit — which is the
honest way around for a descriptive doc.

Pedagogically it makes three choices worth keeping in future docs: data
before code (§2 shows the journal line before any module); the invariant
threaded through every section rather than stated once; and exercises that
trip real gate codes instead of tour the API. Two nits are R6 (the module
count) and the header's branch name (`claude/build-0001`; the merged
branch was `claude/build-0001-ggeipn`). One index omission: the tutorial
was never added to `docs/README.md`'s reading list — fixed in the commit
filing this review.

One structural observation, not a defect: the tutorial restates enough
spec content (footer formats, event vocabulary, gate table) that it will
drift as 0002+ land. Its own defense is the status line ("descriptive, not
normative") plus the normative pointers in the header. The cheap
discipline that keeps it honest: re-run its §12 exercises against the tip
whenever a plan lands — they are executable and will catch most drift on
their own.
